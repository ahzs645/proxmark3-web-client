The **Mifare Attacks Panel** provides a graphical interface for all major Mifare Classic key recovery techniques. All attacks run entirely in the browser via the WASM-compiled PM3 client.

## Supported Attacks

### Autopwn

Automated key recovery that cycles through all available attack methods. This is the recommended starting point — it tries CHK, nested, hardnested, and darkside in sequence.

**In WASM**: Fully functional. Will fall through to hardnested for hard-PRNG cards (like EV1).

### Nested Attack

Recovers unknown sector keys when you already know at least one key. Fast and reliable on cards with a weak (predictable) PRNG.

**In WASM**: Works. Correctly reports "Tag isn't vulnerable to Nested Attack (PRNG is not predictable)" for hardened cards.

### Static Nested

Variant for Chinese clone cards that use static (non-random) nonces. These cards have a predictable PRNG, making key recovery trivial.

**In WASM**: Works.

### Darkside Attack

Exploits a vulnerability in the Mifare Classic PRNG to recover a key with no prior knowledge. Works on original NXP cards but not on newer hardened versions.

**In WASM**: Works. Correctly reports "Card is not vulnerable to Darkside attack" for hard-PRNG cards.

### Hardnested

Advanced attack for cards with a hardened PRNG (EV1, etc.). Collects encrypted nonces from the card and uses statistical analysis to reduce the keyspace, then brute-forces the remaining candidates.

**In WASM**: Fully functional after patching. See [Hardnested in WASM](#hardnested-in-wasm) below for details.

### Key Check (CHK / FCHK)

Validates a list of known keys against all sectors. Two variants:
- `hf mf chk` — standard check, tries keys one at a time
- `hf mf fchk` — fast check, tests all keys in a single command to the PM3

**In WASM**: Both work. A full 4K card check with 61 hardcoded keys takes ~30-54 seconds.

### NACK Bug Test

Tests whether the card is vulnerable to the MIFARE NACK bug.

**In WASM**: Works.

## Usage

1. Navigate to the **Attacks** tab
2. Place a Mifare Classic card on the reader
3. Select your attack type
4. Configure parameters (known keys, target sectors, etc.)
5. Click **Run** — output appears in the terminal

Results include recovered keys per sector, which are automatically available for memory dump operations.

## Hardnested in WASM

The hardnested attack was originally **stubbed out** for the Emscripten build — it silently returned `PM3_ENOTIMPL` with no error message. This has been fixed. Here's what was involved and what to expect.

### What was changed

The upstream PM3 codebase disabled hardnested for WASM because it depends on:

1. **Pthreads** — spawns multiple brute-force threads
2. **SIMD instructions** — uses AVX512/AVX2/SSE2/NEON for fast bitslice cracking
3. **lz4/bz2 libraries** — for loading compressed precomputed state tables

Each was addressed:

| Dependency | Solution |
|-----------|----------|
| Pthreads | Already supported via `-sUSE_PTHREADS=1`. Added `-sPTHREAD_POOL_SIZE=8` and capped threads at 4. |
| SIMD | Forced `NOSIMD_BUILD` path by setting `cpu_arch = wasm` in the hardnested Makefile. Uses 64-bit integer operations instead. |
| lz4/bz2 | Provided inline API stubs so the code compiles. Compressed table paths fail gracefully at runtime. |
| Memory | Increased `MAXIMUM_MEMORY` from 512 MB to 2 GB. |
| SAFE_HEAP | Removed — incompatible with SharedArrayBuffer used by pthreads. |

### What to expect

When running hardnested in WASM, you'll see output like:

```
Start using 4 threads and no SIMD core
Brute force benchmark: 120 million (2^26.8) keys/s    | 140737488355328 | 14d
Loaded 0 RAW / 0 LZ4 / 0 BZ2 in 657 ms
```

The "0 RAW / 0 LZ4 / 0 BZ2" indicates no precomputed bitflip tables were found. This is expected — the tables aren't embedded in the WASM filesystem. The attack proceeds by collecting nonces from the card and reducing the state space through statistical analysis:

```
 Time | #nonces | Activity                             | #states         | time
    1 |       0 | Using 0 precalculated bitflip tables | 140737488355328 | 14d
   19 |    1439 | Apply Sum property. Sum(a0) = 192    |  235168514048   | 33min
   23 |    1763 | Apply bit flip properties            |  197767331840   | 27min
   24 |    1871 | Apply bit flip properties            |  175294234624   | 24min
```

The state count drops from ~2^47 (14 days of brute force) down toward a tractable number. Once reduction is complete, brute force begins using 4 threads with the NOSIMD core.

### Performance comparison

| Metric | Native | WASM (NOSIMD, 4 threads) |
|--------|--------|--------------------------|
| Brute force rate | ~500M-2B keys/s (with SIMD) | ~120M keys/s |
| Typical attack time | 30s - 5min | 5min - 30min+ |
| Memory usage | ~200-500 MB | ~500 MB - 1.5 GB |

The WASM version is roughly 4-8x slower due to no SIMD and WASM overhead, but it **works** — which is the important thing for a browser-based tool.

### Future improvements

- **Embed raw bitflip tables** in the Emscripten virtual filesystem using `--embed-file` or `--preload-file` to speed up the reduction phase
- **WASM SIMD128** — Emscripten supports `wasm_simd128.h` intrinsics which could be added as a new dispatch target in `hardnested_bf_core.c` for ~2-4x speedup
- **Decompress tables at build time** — convert the `.lz4` tables to raw `.bin` format and embed those, avoiding the need for lz4/bz2 at runtime
